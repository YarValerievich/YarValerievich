## [Ambilight WLED](https://github.com/YarValerievich/ambilight-wled)

Разработал аппаратно-программный комплекс для динамической подсветки 85" ТВ. Главная инженерная задача заключалась в построении стабильного end-to-end пайплайна: от захвата видео с камеры до управления 340 зонами WS2812B через ESP32 с задержкой менее 50 мс.

В процессе разработки столкнулся с рядом нетривиальных проблем, которые потребовали доработки архитектуры:

* **Блокировки сетевого ввода-вывода.** Изначально при потере связи с ESP32 mDNS-резолвинг (`wled-tv.local`) блокировал основной поток на 5 секунд на каждом кадре. Переписал транспортный слой: перевел UDP-сокеты в неблокирующий режим и добавил принудительное разрешение IP-адреса только при инициализации. Это обеспечило честную drop-policy без фризов конвейера.
* **Аппаратные артефакты на линии данных.** На тестовых стендах наблюдались сбои цветов и "мертвые" первые пиксели из-за несовпадения логики 3.3В (ESP32) и 5В (лента), а также наводок. Решил проблему внедрением согласователя уровней 74AHCT125 и токоограничивающего резистора 330 Ом непосредственно перед входом DI ленты.
* **Конфликты окружения на ARM64.** Столкнулся с бинарной несовместимостью C-расширений OpenCV и свежего NumPy 2.x на Raspberry Pi 5. Оптимизировал процесс деплоя, разделив тяжелые системные зависимости (установка через `apt`) и изолированные Python-библиотеки в `venv`, что полностью исключило ошибки `binary incompatibility`.
* **Деградация плавности при просадках FPS.** Стандартное сглаживание зависело от частоты кадров. Реализовал алгоритм Time-based EMA, где коэффициент сглаживания рассчитывается динамически на основе реального `dt` между кадрами, делая картинку математически инвариантной к лагам камеры.

**Стек:** Python 3.11, OpenCV, FastAPI, MQTT, WLED, Raspberry Pi 5, ESP32, systemd.

## [RobStride PWM-to-CAN Bridge](https://github.com/YarValerievich/robstride-pwm-bridge)

Разработал надежную прошивку моста на базе STM32F103C8 для трансляции сигналов RC-аппаратуры в команды управления сервоприводом RobStride 00 по шине CAN. Основной фокус был сделан на детерминизме контура управления, отказоустойчивости и безопасной работе с ресурсами микроконтроллера.

В процессе реализации были решены следующие инженерные задачи:

* **Дребезг и шум на линии ШИМ.** Настроил аппаратный захват (PWM Input) на таймерах STM32 в режиме `Slave Reset` с триггером по переднему фронту и включенным аппаратным фильтром (`IC Filter = 8`). Программное скользящее среднее для выбора профиля вынесено из ISR в основной цикл, что минимизировало время пребывания в прерывании и предотвратило потерю кадров.
* **Джиттер в контуре управления.** Реализовал полностью неблокирующую архитектуру опроса телеметрии (напряжение шины, позиция вала) в режиме OPERATION. Асинхронные запросы по CAN гарантируют, что основной цикл Cyclic Synchronous Position (CSP, 100 Гц) не блокируется ожиданием ответов, обеспечивая строгий детерминизм.
* **Целостность данных и обработка отказов.** Внедрил строгий конечный автомат (FSM: INIT → SELFTEST → OPERATION → FAULT) с четким разделением на «жесткие» (мгновенная блокировка, например, при потере PWM или просадке VBUS) и «мягкие» ошибки (попытки восстановления с лимитом бюджета для предотвращения бесконечных циклов перезапуска). Чтение разделяемых float-переменных из ISR защищено критическими секциями (`__disable_irq()`) для предотвращения «рваных» чтений (torn reads).
* **Оптимизация использования стека.** На ресурсоограниченном Cortex-M3 отказался от тяжелых функций форматирования (`snprintf`) в критических путях выполнения в пользу легковесной побайтовой передачи отладочных строк, что исключило риск переполнения стека и возникновения Hard Fault.
* **Защита протокола WS2812.** Передача данных для индикации состояния по SPI обернута в критическую секцию (с опцией перевода на DMA), чтобы прерывания от CAN или таймеров не разрывали строгие временные интервалы протокола, что устраняло артефакты цвета (подмешивание зеленого канала).

**Стек:** C, STM32 HAL, CMSIS, CAN 2.0B, PWM Input Capture, SPI, PlatformIO, логический анализатор.
